# No user request reached worker-b in the ~16 s between becoming ready and the end
# of the run. Interplay of two policies: the ramp starts it at limit 1 and adds a
# load penalty of (dispatch_max - ramp_limit) = 7, shrinking as the limit doubles
# per 5 s poll; prefix_then_load prefers worker-a, the only holder of the shared
# prefix after worker-b's prefixes were forgotten, while it is within the slack (4)
# of the least loaded worker. With 8 clients worker-a's load never exceeds 8, so the
# cold returning worker only takes traffic once the ramp is complete. A longer run
# (1,600 requests) was started to observe it.
