## Interpretation
# The first limiter is the gateway's own dispatch cap (2 in-flight per worker), not
# the GPU: engines never ran more than 2 requests, had an empty queue and ~0 % KV
# while the gateway shed 96 % of run B (264 queue_full + 24 timeout_queue). With
# 2 slots and ~2 s service time, 16 queued requests cannot clear a 5 s queue
# deadline. Next: raise GATEWAY_DISPATCH_CONCURRENCY_PER_WORKER to 8 (= engine
# max_running_requests) and repeat A and B.

## Comparison
# A: 48.8 s -> 14.9 s (3.3x); p50 3.88 -> 0.96 s; p99 5.83 -> 2.08 s; all 200 in both.
# B: completed 12 -> 48; timeout_queue 24 -> 0; queue_full 264 -> 252.
# 48 = (16 queued + 8 dispatched) x 2 workers: the admission bound; everything
# beyond it got an immediate 503 queue_full (with Retry-After) instead of waiting.
# KV usage stayed ~0 %: ~1,100-token prompts with ~97 % prefix-cache hits are small.
# Grafana "placements per worker" during B and B': worker-a received ~5x the
# placements of worker-b (herding: least-loaded on metrics up to 5 s old, ties go to
# the first worker). queue_full is raised after placement, so requests were shed on
# a full worker-a queue while worker-b had room: queue depth must be part of the
# placement score/eligibility, not only an admission input.
