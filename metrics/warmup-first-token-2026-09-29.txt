# Cold vs warm first-token latency - 29 September 2026
# Host: Lambda 1x H100 80GB HBM3 (SXM5), two SGLang v0.5.20 workers (Qwen3-8B BF16)
# on 38,000 MiB HAMi slices. Release 34e6b32. Raw output pasted by the user.
#
# Method: experiments/first_token.py, run inside the gateway image (httpx), sends 6
# sequential chat requests directly to one worker's NodePort. Each request has the
# same ~1,650-token system prefix (a course passage repeated 40x, synthetic but
# app-shaped: shared prefix + unique question) and a different question.
# max_tokens=1, so the latency is prefill + first token: our TTFT proxy. The gateway
# path cannot be used for this because it does not stream and cannot target a
# specific worker. Measured client-side, includes HTTP overhead on the host.
#
# Cold replica: sglang-1 deleted, recreated, measured right after Kubernetes Ready.
# Before our run, sglang-1 had only served SGLang's own startup warmup (6 tokens),
# health probes (1 token) and the gateway's warmup (64 tokens); never our prefix.

## Final summary (4 fresh restarts + 26 requests on the older replica)
# - Cold shared prefix: 54, 72, 73, 72 ms. Warm (prefix cached, new question):
#   15-17 ms. Cold/warm = 3.4-4.5x.
# - Fresh replica: exactly one ~100 ms request (98, 99, 103, 98 ms) in every
#   restart, 4/4; in 3/4 it was request 4. Never more than one in 20 requests.
# - Older replica: 0 outliers in 26 requests. Random 1-in-6 noise would predict
#   ~3-4. Conclusion: a one-time cost on a fresh replica, not noise. Mechanism
#   not established (candidate: first-time kernel selection for a new shape).
# - Fully cached repeats (runs 7-20) took 24-30 ms, more than the 15-17 ms of
#   15-token extends; SGLang logs 1-token prefills with "cuda graph: False"
#   (smallest prefill graph is 4 tokens) - a likely but unverified explanation.
